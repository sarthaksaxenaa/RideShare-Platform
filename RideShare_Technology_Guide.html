1. Next.js — Frontend Framework

Next.js is a React framework by Vercel. Adds server-side rendering, file-based routing, and optimized builds on top of React.

Why We Use It

  • File-based routing — app/login/page.tsx → becomes /login
  • Server Components — Render on server for faster load & SEO
  • Client Components — 'use client' for interactive UI
  • Code splitting — Each page loaded only when needed
// Server Component (default) — no hooks allowed
export default function Page() {
  return <h1>Renders on server</h1>
}

// Client Component — hooks & interactivity
'use client';
export default function Form() {
  const [name, setName] = useState('');
  return <input value={name} onChange={e => setName(e.target.value)} />
}

2. React — UI Library

Component-based UI library. Every piece of UI is a reusable function.

Core Hooks

// useState — manage local state
const [pickup, setPickup] = useState('');
setPickup('NIET College');  // → re-renders

// useEffect — side effects (API calls, subscriptions)
useEffect(() => {
  fetchNotifications();
  return () => cleanup();  // runs on unmount
}, [dependency]);  // re-runs when dependency changes

// useCallback — memoized function reference
const handleBook = useCallback(() => {
  socket.emit('trip:request', data);
}, [socket, data]);

// useMemo — memoized computation
const center = useMemo(() => pickupCoords || DEFAULT, [pickupCoords]);
💡 Interview: "React uses a Virtual DOM. On state change, it diffs the new virtual DOM with the old one and only updates changed nodes. This is called reconciliation."

5. Zustand — State Management

Lightweight alternative to Redux. 1KB vs 7KB, minimal boilerplate.

import { create } from 'zustand';
import { persist } from 'zustand/middleware';

export const useAuthStore = create(
  persist(
    (set) => ({
      user: null,
      isAuthenticated: false,
      login: (user, token) => set({ user, token, isAuthenticated: true }),
      logout: () => set({ user: null, isAuthenticated: false }),
    }),
    { name: 'auth-storage' }  // Auto-saves to localStorage!
  )
);

// Use anywhere:
const user = useAuthStore((s) => s.user);

7. Node.js + Express — Backend

Node.js = JS runtime for servers. Express = Web framework.

Request → CORS → JSON Parser → Rate Limiter → Auth → Route Handler → Response
// Middleware: runs before route handler
function authenticate(req, res, next) {
  const token = req.cookies.jwt;
  if (!token) return res.status(401).json({ error: 'Unauthorized' });
  req.user = jwt.verify(token, SECRET);
  next();  // Pass to next handler
}

// Route handler
app.get('/api/trips/:id', authenticate, async (req, res) => {
  const trip = await prisma.trip.findUnique({ where: { id: req.params.id } });
  res.json(trip);
});
💡 Pattern: Express uses Chain of Responsibility — each middleware either responds or calls next().

12. bcrypt — Password Hashing

// Hash (registration): one-way, irreversible
const hash = await bcrypt.hash("MyPass123", 12);

// Compare (login): never decrypts
const valid = await bcrypt.compare(input, storedHash);

🎯 Top 10 Interview Q&As

Q1: "How does real-time tracking work?"

"Socket.io maintains a persistent WebSocket connection. When a driver moves, their app emits driver:location. The server relays it to the rider's socket, updating the map instantly. No polling needed."

Q2: "How do you handle authentication?"

"Dual-token JWT. Access token (1h) for API calls. Refresh token (30d) in HttpOnly cookie with restricted path. Axios interceptor auto-refreshes on 401. Users stay logged in 30 days like Ola/Uber."

Q3: "Why Zustand over Redux?"

"1KB vs 7KB, zero boilerplate, built-in persistence. For auth/trip/socket state, Zustand's simplicity is ideal. No actions, reducers, or dispatch overhead."

Q4: "How does payment work?"

"Stripe authorize-then-capture. On booking: hold funds (no charge). On complete: capture actual fare. On cancel: release hold instantly. Avoids 5-10 day refund cycle."

Q5: "How do you verify the correct rider?"

"4-digit PIN generated on trip creation, shown to rider only. Driver must enter it to start the trip. API hides PIN from driver requests — they get it verbally."

Q6: "What if the server crashes mid-trip?"

"State is in PostgreSQL, not memory. On restart, server reads from DB. Socket.io auto-reconnects. Frontend polls API as WebSocket fallback."

Q7: "How does surge pricing work?"

"Time-based multipliers: peak (1.3×), late night (1.5×), weekends (1.4×). They stack — late-night weekend = 2.1×. In production, add supply/demand ratio."

Q8: "Why PostgreSQL over MongoDB?"

"Highly relational data — Users→Trips, Trips→Riders/Drivers. PostgreSQL handles JOINs and foreign keys natively. MongoDB would need manual denormalization."

Q9: "How do you handle rate limiting?"

"In-memory limiter. Auth: 30 req/5min. API: 120/min. Prevents brute-force while allowing normal usage. Production: Redis for distributed limiting."

Q10: "Explain the database schema."

"Core: User, Trip, SavedLocation. User has role for RBAC. Trip has dual foreign keys (riderId, driverId) with named Prisma relations. UUIDs for all IDs. PromoCode, Notification, OTP for business features."
